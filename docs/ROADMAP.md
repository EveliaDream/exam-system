# 学生考试系统 · 开发路线图

> 项目：`exam-system`（Spring Boot 4.1.1 / Java 17）
> 目标：用大学软件工程能力可完成的在线考试系统，不涉及 AI 判分等复杂技术
> 技术选型：Vue3 + Element Plus 前后端分离 / Spring Security / 不引入 Redis 与 WebSocket

---

## 一、范围界定

### 主线闭环（必做）

```
教师建题库 → 组卷 → 发布考试 → 学生限时作答 → 客观题自动判分 → 成绩统计 → 教师看报表
```

### 明确不做（控制工期的关键）

| 不做 | 理由 |
|---|---|
| 主观题 AI 判分 | 技术风险高、评分不可解释，答辩易被质疑 |
| 人脸识别 / 摄像头监考 | 技术与合规双重风险 |
| 编程题在线运行（OJ） | 需要容器沙箱，体量等同另一个项目 |
| 分布式 / 微服务 / 消息队列 | 单体应用完全够用，引入只增加风险 |
| 多租户、多学校 | 无意义复杂度 |

### 加分项（时间富余再做，不要一开始就规划）

- 切屏次数记录、考试中实时监考看板（轮询实现）
- 成绩 Excel 导出
- 成绩分布统计图表（ECharts）
- 操作日志审计

## 三、数据模型（11 张表，第一步定稿）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `user` | id, username, password(BCrypt), real_name, role, class_id, status | 学生/教师同表，role 区分 |
| `class` | id, name, grade, teacher_id | 班级 |
| `course` | id, name, teacher_id | 课程 |
| `question` | id, type, stem, options(JSON), answer(JSON), score, difficulty, course_id, created_by | **单表多题型** |
| `exam` | id, title, course_id, total_score, pass_score, start_time, end_time, duration, shuffle, status, created_by | 试卷定义 |
| `exam_question` | exam_id, question_id, score, sort_order | **组卷快照，关键** |
| `exam_class` | exam_id, class_id | 发布范围 |
| `exam_record` | id, exam_id, student_id, start_time, submit_time, objective_score, status | 一次作答 |
| `answer` | id, record_id, question_id, student_answer(JSON), score, is_correct | 作答明细 |
| `operation_log` | id, user_id, action, target, ip, created_at | 审计 |
| `notification` | id, user_id, content, is_read | 可选 |

### 四个必须想清楚的设计点

1. **`question` 单表多题型**
   `type` 取值 `SINGLE / MULTIPLE / JUDGE / BLANK`；`options` 与 `answer` 用 JSON 字符串列存储。
   不要为每种题型建一张表，JOIN 与判分分支会迅速失控。

2. **`exam_question` 必须是快照**
   组卷时把题目 ID + 分值复制进该表。否则教师修改题库会导致**已考完的考试成绩变化**。
   这是答辩最常被抓的逻辑漏洞，也是最高频的踩坑点。

3. **试卷实例化时机**
   学生点击"开始考试"时才创建 `exam_record` 并预填 `answer` 行，而非发布考试时全班生成，避免数据量爆炸。

4. **权威倒计时在服务端**
   `deadline = min(start_time + duration, end_time)` 由后端计算，每次提交都校验。
   前端倒计时仅为显示。必须防止用 Postman 绕过前端超时提交。

### 填空题判分（不引入 AI）

标准化匹配，约 30 行代码，覆盖 95% 场景：

```
去首尾空格 → 去全部空白字符 → 统一大小写 → 全角转半角
→ 与 answer(JSON 数组，支持多个可接受答案) 逐一比对
```

### 阶段 2 · 用户与班级管理（4~6 天）✅ 已完成

- ✅ 学生分页查询（按班级、关键词、状态筛选）
- ✅ 学生 CRUD：新增（可指定初始密码）、编辑（改资料 / 调班）、删除

- ✅ 批量导入：纯文本逐行处理（`用户名,姓名,年级,班级名称`），失败行返回原因，班级自动创建
- ✅ 班级 CRUD + 学生人数统计；班级内仍有学生时禁止删除
- ✅ **教师数据隔离**：教师只能看到/操作自己名下班级的学生；未分班学生视为待分配资源
- ✅ 前端：AdminLayout（侧边菜单 + 顶栏）、学生管理页（筛选/表格/分页/表单/导入对话框）、班级管理页

**验收结果**：`./mvnw test` **46 个用例全绿**（阶段 2 新增 37 个）；
`node docs/scripts/e2e-phase2.mjs` **26 项全通过**；前端 `vite build` 构建成功。

> 阶段 2 的关键收获：**权限边界要做两层** —— `@PreAuthorize` 只解决"学生不能访问教师接口"，
> 还要用 SQL 把教师的数据范围限制在自己名下的班级，否则教师 A 能改教师 B 的学生。

### 阶段 3 · 题库与知识点管理（4~6 天）— 进行中

> **为什么知识点必须在阶段 3 落地**：学情分析的口径是「按知识点聚合作答正确率」。
> 若阶段 5 已经产生历史作答数据、阶段 6 才补知识点，那批数据将无法参与统计（不可逆的顺序依赖）。

- ✅ 四种题型增删改查、启用/停用
- ✅ 筛选：课程、题型、难度、**知识点**、关键词、启用状态
- ✅ 录入校验：单选答案唯一且为合法选项标识、多选答案 ≥2 项且不重复、判断答案必须 T/F、填空题至少一个可接受答案、选项不可重复、分值 > 0
- ✅ **知识点管理**：课程归类、同课程内名称唯一、被题目引用时禁止删除（防止学情统计出现空洞）
- ✅ **题目 × 知识点多对多关联**：综合题可挂多个知识点；题目列表批量取标签，避免 N+1
- ✅ 课程下拉选项接口（课程的完整 CRUD 留待后续）
- ⬜ 图片题干上传（可选，`MultipartFile` 存本地目录）
- ⬜ 题库 Excel 批量导入

**验收**：每种题型各造 5 题，均能正确回显与编辑；每题至少关联 1 个知识点。

### 阶段 4 · 组卷与考试发布（5~7 天）

- 手动选题组卷 + 按题型/难度随机抽题（去重）
- **强校验：题目分值之和 == 试卷总分**
- 发布：绑班级、时间窗、时长、选项乱序、及格线、限考次数
- 考试列表三态：草稿 / 已发布 / 已结束

**验收**：教师发布 10 题考试，学生在"我的考试"中可见。

### 阶段 5 · 在线作答与自动判分（7~10 天，**核心**）

- 进入考试：创建 `exam_record` + 预填 `answer` → 返回**不含答案的**题面 DTO
- 前端答题界面 + 倒计时（服务端签发的 deadline 为准）
- 自动保存：改答案即提交 + 30 秒兜底轮询；断线重进恢复答案
- **上报每题作答耗时与修改次数**（`answer.time_spent_sec` / `submit_count`）：
  耗时必须用「离开该题时间戳 − 进入该题时间戳」计算，不能用 `setInterval` 累加
  （后台标签页定时器会被浏览器降频，导致耗时严重失真）。这是阶段 6 交叉分析的数据来源。
- 提交：服务端校验时间窗 → 自动判分 → 写 `objective_score` → 状态置为已提交
- 超时服务端兜底自动提交
- 防作弊（仅做服务端可验证项）：切屏次数上报、提交耗时异常记录

**验收**：三种客观题判分正确；直接调接口无法超时提交；断网重进答案不丢。

### 阶段 6 · 学情分析与收尾（6~8 天，**项目的创新性核心**）

> 本阶段是「学情数据驱动」定位的落地点，不只是画图表，而是输出教师能直接行动、学生能直接执行的建议。

- **知识点掌握度计算**：按知识点聚合正确率
  `掌握度 = Σ(该知识点下答对题的分值) / Σ(该知识点下全部题的分值)`（按分值加权，避免题量不均导致失真）
- **学生端：薄弱知识点推送**：判卷完成后按掌握度升序取前 3~5 个知识点，
  同时给出「错题数」与「掌握度百分比」，并附同类练习题入口，使考试结果转化为复习任务
- **教师端：题目难度 × 学生水平贴合度**（替代统计门槛过高的「区分度」）
  - 班级水平 = 全班平均得分率；题目难度 = 该题平均得分率
  - 相对比较：某题难度显著低于班级水平 → 偏难，提醒复核；显著高于 → 偏易、无考查价值
  - **与作答耗时交叉判断**：得分率低且耗时短 → 可能超纲或表述不清；
    得分率低但耗时长 → 属真实难点，不必改题。单看耗时没有意义，必须与得分率交叉
- **样本量门槛（必须实现）**：作答人数 < 30 或高低分组各不足 8 人时，
  标注「数据不足，仅供参考」，不给出定量结论，避免误导
- 教师：成绩单、按班级筛选、导出 Excel
- 统计：平均分 / 最高最低 / 及格率 / 分数段分布（ECharts）
- 补齐核心 Service 单元测试与集成测试
- 文档：需求分析、数据库设计（E-R 图 + 表说明）、接口文档、用户手册、答辩 PPT
- 一键初始化 SQL（含演示数据）+ 演示脚本

**总计约 7~8 周**；若 AI 承担大部分编码、人工专注审查与测试，可压缩至 4~5 周。

## 五、AI 协作规范

| 适合完全交给 AI | 必须自己拍板 |
|---|---|
| 实体类、Repository、样板 CRUD Service | **数据库表设计与关系**（答辩必问，返工成本最高） |
| Vue 页面与 Element Plus 布局 | **判分规则与边界条件**（超时、重复提交、部分给分） |
| SQL、`data.sql` 演示数据 | **权限边界**（谁能看谁的卷子） |
| 单元测试用例、正则、工具类 | **组卷快照等一致性设计** |
| 异常处理、参数校验、日志 | 业务规则取舍 |

### 三条硬规则

1. **一次只让 AI 做一个模块**，并明确提供：表结构 + 接口签名 + 验收标准。
2. **每个模块交付后立刻写 2~3 个测试再往下走**，尤其验证边界条件。
3. **每阶段结束跑完整链路并 Git 打 tag**，避免最后一周"改崩了没得退"。

## 六、认证方案说明（JWT 的已知取舍）

因已删除 Redis，JWT 无法做服务端主动失效，需在文档中如实说明：

- **登出**：前端清除本地 token；后端无法立即吊销（可加 `token_version` 字段或短过期时间缓解）
- **改密码后**：旧 token 在过期前仍然有效，需配合短过期时间（如 2 小时）
- 这是可接受的工程取舍，答辩时主动说明比被问出来更好
