## 毕设题目：

**基于 Spring Boot 与 Vue 的在线考试与题库系统**

---

## 要解决的问题是什么？

本课题要解决的是高校课程考核中「组织成本高、反馈周期长、过程性考核难以落地」的现实问题，具体包含三个方面。

第一，传统纸质考试的组织成本高。出卷、印制、监考、收卷、人工阅卷、登分、成绩统计等环节都依赖人工，一门课程一次考试往往需要教师投入数小时甚至数天；人工阅卷还不可避免地存在漏判、错判与登分差错，成绩的准确性与可追溯性都难以保证。

第二，成绩反馈周期长，考试的教学价值被削弱。学生通常要等数天才能知道成绩，此时教学进度早已推进，学生无法针对薄弱环节及时查漏补缺；教师也难以在学期中途掌握全班的知识掌握情况，教学调整往往滞后。

第三，过程性考核因组织成本过高而难以常态化。教育评价改革倡导加强过程性考核，但平时测验、单元小测如果每次都走一遍纸质考试流程，教师的时间成本无法承受，结果往往是「一考定成绩」。

对于已有的在线考试产品，还存在两方面不足：一是成熟商业平台（如各类教学平台）功能完备但体量庞大、操作路径深，教师难以按课程特点定制组卷规则与成绩统计口径，且数据存放在第三方平台；二是部分系统只做「题库增删改查 + 在线答题」，缺少对考试完整生命周期与历史数据一致性的考虑。

因此，本课题要做一个面向高校课程、可自主部署、聚焦客观题考核的轻量级在线考试系统，把「出题—组卷—考试—判分—统计」整条链路线上化，让客观题自动判分、成绩实时生成，既降低教师的重复劳动，也使过程性考核在时间上变得可行。

## 课题背景（国家社会、经济、产业（行业）等）？

从国家政策层面看，《教育信息化 2.0 行动计划》等文件明确要求推动信息技术与教育教学深度融合，教育评价改革也持续倡导改进结果评价、强化过程评价、探索增值评价。考试作为教学评价的核心环节，其信息化、自动化程度直接影响评价改革的落地效果，这为本课题提供了明确的政策背景。

从社会与教育实践层面看，高校在校生规模持续扩大，课程数量与考核频次同步增长，教务与任课教师面临的考务压力逐年上升。与此同时，线上教学已成为常态，教师与学生都习惯了线上完成作业与测验，对在线考试系统的接受度和依赖度显著提高。

从产业与技术层面看，Java 生态与前端工程化都已相当成熟：Spring Boot 通过「约定优于配置」与丰富的 starter 依赖大幅降低了后端开发门槛，Vue 3 的响应式系统与组件化开发适合构建交互复杂的考试界面，MySQL 足以支撑课程级应用的并发与数据量。这些成熟技术使一个本科阶段的学生能够在有限周期内独立完成一个具备实用价值的完整系统，技术风险可控。

从教学场景的特殊性看，随堂测验、期中考试这类考核往往集中在同一时间段内发起请求，是对系统稳定性要求较高的场景；同时，考试数据涉及成绩与公平性，对「历史成绩不能被后续修改影响」有严格要求。这要求系统在架构与数据模型设计上做针对性考虑，也构成了本课题的技术价值所在。

## 创新性？

本课题的选题并非全新领域，创新性主要体现在「针对课程级场景的取舍与设计改进」，可分为设计创新、技术创新与工程实践三个方面。

一、设计创新：试卷快照与题库解耦。

同类系统常见的做法是试卷仅保存题目编号，判分时回查题库，一旦教师后续修改题目或答案，历史考试的判分结果就会随之改变，成绩失去可追溯性。本系统在组卷时把题干、选项、正确答案、解析与分值完整固化到独立的组卷快照表中，判分只读快照、不再回查题库，从数据结构上消除了「改题导致历史成绩变化」的可能。这是本系统最关键的设计决策。

二、设计创新：服务端权威计时与断点续考相结合。

考试时限完全由服务端按「开始作答时间 + 时长」与「考试结束时间」取较早者计算，前端倒计时仅用于显示，每次提交都重新校验，避免绕过前端超时提交；同时进入考试即预填作答明细行、作答过程直接更新数据库，使刷新页面或断线重进能够恢复已答内容，且不需要引入额外的缓存中间件。两者结合，在保证考试公平性的同时兼顾了作答体验。

三、技术创新：用 token 版本号替代缓存中间件实现登录态失效。

JWT 是无状态凭证，服务端无法主动吊销，通常需要借助 Redis 黑名单解决，这会给课程级应用增加一个必须部署的中间件。本系统在用户表上引入 token 版本号，改密码、重置密码、停用账号时版本号加一，认证过滤器比对版本号即可让旧令牌立即失效。方案轻量、无额外依赖，且语义清晰。

四、技术创新：两层权限边界保证教师之间的数据隔离。

仅用角色注解只能拦截学生访问教师接口，无法阻止教师之间互相查看或修改对方的数据。本系统把数据范围条件直接写进查询语句（教师只能看到自己名下班级的学生，未分班学生视为公共待分配资源），并在写操作前二次校验，同时保证分页总数与实际可见数据一致。

五、工程实践：以可交付、可复现为标准的开发方式。

项目用「开发 / 交付 / 测试」三套独立配置区分不同环境；用数据库结构校验代替自动建表，让表结构漂移在启动阶段就暴露，并以建表脚本作为表结构的唯一依据；编写了覆盖认证、权限、数据隔离与业务规则的集成测试，以及两个可直接运行的端到端验证脚本，使系统状态可随时复现，而不是只能在开发者本机上运行。

## 项目（系统）需求是什么？

系统面向教师与学生两类角色，需求分为功能性与非功能性两部分。

一、功能性需求。

1. 用户与权限：教师与学生用统一入口登录，按角色区分可见功能；支持修改密码；账号可启用与停用，停用后无法登录且已登录状态立即失效。
2. 学生与班级管理（教师）：学生信息的增、删、改、查与分页，支持按班级、姓名或用户名、启用状态筛选；支持批量导入学生名单；支持把学生分配到班级、调整班级、重置学生密码。
3. 题库管理（教师）：按课程维护单选、多选、判断、填空四种题型，支持题干、选项、正确答案、解析、难度与分值的录入与修改，支持按课程、题型、难度、关键词筛选，题目可启用或停用。
4. 组卷与考试发布（教师）：支持手动选题与按题型、难度随机抽题两种组卷方式，形成试卷并固化快照；发布时设置考试时间窗、作答时长、及格线、限考次数、是否乱序，并指定面向的班级；考试具备草稿、已发布、已结束三种状态。
5. 在线作答（学生）：在考试时间窗内进入考试，页面显示权威倒计时与答题卡；作答自动保存，刷新或断线后重新进入可恢复已答内容；到时未提交由服务端自动收卷。
6. 自动判分与成绩查询：交卷后客观题自动判分并即时出分；学生可查询本人历次成绩与答题详情（含正确答案与解析）；教师可查看指定考试的成绩单，并按班级统计平均分、最高最低分、及格率与分数段分布。

二、非功能性需求。

1. 性能：课程级规模下的并发能力（单场考试几十至上百人同时作答与交卷），在普通教学服务器上响应时间应保持在秒级以内。
2. 安全：口令使用 BCrypt 加盐哈希存储，不保存明文；接口按角色鉴权并做数据范围隔离；学生端题面接口不得返回正确答案，判分全部在服务端完成；关键操作留痕可追溯。
3. 可靠性：作答内容实时保存，异常退出后可恢复；考试时限以服务端为准；同一学生对同一场考试不得产生重复作答记录。
4. 易用性：教师端以表格与表单为主，操作路径浅；成绩单与统计结果直接服务教学决策，统计口径（如及格率）与教师设定的及格线保持一致。
5. 可维护性：统一的接口响应结构与错误码规范、分层清晰的代码结构、可复现的部署与初始化流程，并以自动化测试保证核心业务规则不被后续修改破坏。

## 系统具有哪些功能？

系统按角色划分功能模块，教师端五个模块、学生端三个模块。

一、教师端功能。

1. 认证与个人中心：登录、登出、查看当前用户信息、修改密码。
2. 学生管理：学生列表分页查询（支持按班级、关键词、状态筛选）、新增学生（可指定初始密码）、编辑学生资料、调整所属班级、启用与停用账号、删除学生、重置密码、批量导入学生名单。其中删除与停用做了区分：已有考试作答记录的学生不允许删除，只能停用，以保证成绩可追溯。
3. 班级管理：班级列表与分页查询、新增与编辑班级、删除班级（班级内仍有学生时拒绝删除并提示）、查看各班级学生人数。
4. 题库管理：四种题型的题目新增、编辑、删除、启用与停用，按课程、题型、难度、关键词筛选，录入时对单选答案唯一性、多选答案数量、分值范围进行校验。
5. 组卷与考试管理：手动选题或按题型与难度随机抽题组卷、设置每题分值与试卷总分并校验两者一致、发布考试（考试时间窗、作答时长、及格线、限考次数、题目与选项乱序、面向班级）、考试状态管理（草稿 / 已发布 / 已结束）。
6. 成绩与统计：按考试与班级查看成绩单、查看学生答题详情、统计平均分、最高分、最低分、及格率与分数段分布。

二、学生端功能。

1. 我的考试：查看面向本人所在班级、且在时间窗内的考试列表，区分未开始、进行中、已结束。
2. 在线作答：进入考试后显示题目、答题卡与倒计时；支持单选、多选、判断、填空四种题型的作答；作答自动保存，可中断后继续；到点自动收卷。
3. 我的成绩：查询本人历次考试成绩，查看每道题的作答情况、正确答案与解析。

三、系统级功能（由后端保障）。

统一响应与错误码规范、全局异常处理、基于 JWT 的登录态管理、按角色与数据范围的访问控制、关键操作日志留痕、数据库初始化与建表脚本、开发与交付环境的配置切换。

## 核心开发技术是什么？

系统采用前后端分离的 B/S 架构，前后端通过 RESTful 接口通信，技术栈均为本科阶段系统学习过的主流技术，具体如下。

一、后端。

1. 开发语言与运行时：Java（JDK 25），使用 record、文本块等现代语法组织数据传输对象与 SQL 片段。
2. 应用框架：Spring Boot 4.1.1，提供自动配置、内嵌 Tomcat 与可执行 JAR 打包能力；业务层使用 Spring MVC 组织 RESTful 接口。
3. 持久层：Spring Data JPA + Hibernate 7，以实体类表达领域模型，用派生查询与方法级 JPQL 完成数据访问；选项与答案等变长数据以 JSON 字符串存放于文本列，避免为每种题型单独建表。
4. 数据库：MySQL 8（开发与交付环境）、H2 内存库（测试环境）。
5. 安全框架：Spring Security + JWT，采用无状态认证；口令使用 BCrypt 加盐哈希；接口层用方法级注解控制角色访问，数据层用查询条件限定教师可见范围。
6. 参数校验与异常处理：Jakarta Bean Validation 做入参校验，全局异常处理器统一把业务异常与校验失败转换为规范的响应结构。
7. 辅助工具：Lombok 减少样板代码；Maven 进行依赖管理与构建。

二、前端。

1. 框架与语言：Vue 3（组合式 API）+ JavaScript。
2. 构建工具：Vite 6，开发期通过代理把接口请求转发到后端，从根本上避免跨域配置问题；构建产物可直接输出到后端静态资源目录，最终交付为单个可执行 JAR。
3. UI 组件库：Element Plus，配合其中文语言包；图表统计可使用 ECharts。
4. 状态管理：Pinia 管理登录态；Vue Router 负责路由与基于角色的访问守卫。
5. 网络请求：Axios 统一封装，请求拦截器自动附加令牌，响应拦截器统一处理未登录、无权限与业务错误提示。

三、工程与测试。

1. 版本控制：Git。
2. 测试：JUnit 5 + MockMvc 编写覆盖认证、权限、数据隔离与业务规则的集成测试；另提供可直接运行的 Node.js 端到端验证脚本，用于联调与交付验收。
3. 部署：打成单个可执行 JAR，内置 Tomcat，只需 JDK 与 MySQL 即可运行，不依赖外部容器。

四、关于两个「没有使用」的技术说明。

项目前期曾引入 Redis 与 WebSocket 依赖，经评估后移除：作答自动保存采用预填作答明细行、实时更新数据库的方式，既保证答案可靠又不需要额外中间件；实时性需求（如考试过程监控）可用短周期轮询满足，引入 WebSocket 会显著增加连接管理与鉴权传递的复杂度。这一取舍体现的是「技术选型服务于实际需求」而非堆叠技术组件。

## 系统（产品）形式是什么（Web应用系统、网站、微信小程序、移动应用…）？

系统采用 B/S（浏览器/服务器）架构，产品形式是基于浏览器的 Web 应用系统。

教师与学生只需通过浏览器访问统一入口并登录，无需安装任何客户端；系统按登录账号的角色自动呈现对应的功能菜单与页面。

前端为单页应用（SPA），页面切换不刷新浏览器；后端提供 RESTful 接口，前后端完全分离，便于分别开发与后续扩展。

交付形态为单个可执行 JAR 包（内嵌 Tomcat）配合 MySQL 数据库，部署时只需 JDK 与 MySQL 环境，不依赖外部 Web 容器，便于在不同机器上复现与演示。

后续如需扩展到移动端，可在此基础上单独开发微信小程序或移动应用，复用现有的后端接口，不需要改动服务端业务逻辑。

## 项目（系统）开发实现的难点、重点分别是什么？

本项目的重点在于「把考试的完整生命周期做得正确、可追溯」，难点集中在对异常情况与数据一致性的处理上，而不是框架本身的用法。

一、开发重点。

1. 数据模型设计，尤其是组卷快照。试卷必须与题库解耦：组卷时把题干、选项、正确答案与分值固化到快照表，判分只读快照。这是保证历史成绩稳定的前提，也是本项目最核心的设计。
2. 客观题自动判分的准确性。四种题型的判分规则不同：单选、判断要求完全一致，多选要求答案集合完全一致，填空需要做答案标准化处理（去首尾空格、去全部空白字符、统一大小写、全角转半角）并支持多个可接受答案，以覆盖同一答案的不同书写方式。
3. 两层权限边界。既要按角色控制模块访问，又要把教师的数据范围限定在其名下班级，且隔离条件必须写进查询语句，否则分页总数会把不可见数据算进去。
4. 作答过程的可靠性。要保证答案不丢（自动保存）、断线可续（重进恢复）、超时可控（服务端权威时限）与交卷幂等（同一学生同一场考试不产生重复记录）。

二、开发难点及处理方式。

1. 难点：无状态认证无法主动吊销令牌。JWT 一旦签发，在过期前服务端无法使其失效，导致「改密码后旧登录态仍然有效」。处理方式：在用户表引入令牌版本号，改密码、重置密码、停用或删除账号时版本号加一，认证过滤器比对版本号，不一致即判定失效，从而在不引入 Redis 黑名单的前提下解决该问题。
2. 难点：考试时限可能被绕过。若以前端倒计时为准，学生可以通过直接调用接口在超时后继续提交。处理方式：时限完全由服务端按开始作答时间与考试结束时间计算，每次提交重新校验并拒绝超时请求。
3. 难点：教师之间的越权访问。初始设计只做了角色鉴权，教师甲仍可查看或修改教师乙名下的学生。处理方式：在查询条件中加入数据范围限制，并在写操作前二次校验归属，同时特别处理「尚未分班的学生应视为公共待分配资源」这一规则，否则新建账号将无法分班。
4. 难点：删除账号与保留成绩之间的矛盾。直接删除学生会导致成绩单出现指向不存在用户的孤儿记录。处理方式：已有作答记录的学生不允许删除，只能停用；删除采用逻辑删除并同时使该账号的登录态失效。
5. 难点：枚举与中文数据的存储一致性。表结构中包含多种枚举类型与大量中文题干，需统一保证字符集为 utf8mb4，否则出现乱码；同时需保证手写建表脚本与实体定义完全一致，避免出现「只有用框架自动建表才能跑」的隐患。处理方式：以建表脚本作为表结构的唯一依据，并启用结构校验模式，使不一致在启动阶段即暴露。
6. 难点：技术栈版本差异带来的额外成本。项目使用的 Spring Boot 4 与网上多数教程所用的 3.x 在依赖组织上差异较大（依赖名称调整、JSON 库升级并更换包名），照搬教程会直接编译失败。处理方式：以官方文档为依据逐项排查，并把差异与结论整理成文档，避免重复踩坑。
